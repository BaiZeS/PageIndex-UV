# PageIndex-UV 语料统一结构树（Corpus Tree）整体规划

> 日期：2026-08-04　状态：规划稿（未实施）
> 核心命题：**把 PageIndex"单文档结构化推理"推广到多文档——给语料库建一棵领域层级的统一结构树，
> 用同一套"树上推理导航"贯穿 领域→类目→文档→节点。**

---

## [S1] 核心洞察

PageIndex 单文档之所以强，是因为"**先建树、再在树上推理导航**"：
`get_document_structure()` 拿到树 → LLM 推理 → `get_page_content(pages)` 取紧凑范围。
这是"推理-导航"，不是"打分-排序"。

**现状的不对称**：
- **单文档内**：有真正的结构树（章节节点），树搜索推理可用。
- **语料级**：只有**扁平机制**——L0 多通道召回 + `_hierarchy_boost` 标签加权 + map-reduce 选档。
  领域层只是 closet_tags 扁平标签，**不是一棵树**。

**推广思路**：把结构树**向上延伸**，建一棵贯穿语料库的统一树：

```
ROOT（知识库）
└── 领域 Domain（LLM 生成 + 摘要）
    └── 类目 Category（LLM 生成 + 摘要）
        └── 文档 Document（叶子，挂接其章节树）
            └── 节点 Node（章节，现有单文档树）
                └── 子节点 …
```

整库变成**一棵树**，同一套"推理-导航"在每一层复用——这就是把单文档范式推广到多文档。
（对应原文 README 的 *PageIndex File System*：file-level tree indexing，让 PageIndex 对整个语料库推理。）

---

## [S2] 与既有三层重构的关系

三层重构（T7/T8/T9）建的是**三个独立机制**；语料树把它们**统一成一棵树 + 一套导航**：

| 既有 | 语料树中的归宿 |
|:---|:---|
| L0 多通道召回（T7） | 保留，作为**树导航的候选入口/兜底**（海量下先粗筛再上树） |
| `_hierarchy_boost` 标签软路由（T8） | **升级**为树中"领域/类目"层的结构化导航（不再是扁平加权） |
| map-reduce 推理选档（T9） | **泛化**为树上每一层的"推理挑选"（领域层→类目层→文档层逐级） |
| 单文档树搜索（L2/L3） | 保留，作为树的**最底层**（文档内节点导航） |

**不是推翻三层重构，而是给它一个统一的树骨架**：closet_tags / 实体图谱 / 向量 是建树的原料，三层逻辑变成树导航在不同层级的体现。

## [S3] 语料树构建（离线，索引期）

**输入**：每篇文档的章节树 + closet_tags（抽象语义标签）+ 实体图谱 + 本地向量（bge-small-zh）。

**步骤**：
1. **文档向量化**：用 bge-small-zh 对每篇的标题+摘要+标签编码。
2. **层级聚类**：对文档向量做层次聚类（或按 closet_tags 的抽象标签分组），形成"类目→领域"候选簇。
3. **LLM 定名 + 摘要**：对每个簇，让 LLM 生成领域/类目名称与一句摘要（供导航时给 LLM 看）。
4. **组装树**：ROOT→领域→类目→文档→（挂接各文档章节树）。
5. **存储**：新增 `corpus_tree` 表（或 JSON 字段）存整棵树；每节点带 `{title, summary, level, children}`。
6. **增量更新**：文档增删时，局部更新所属类目/领域簇（不必全量重建）。

**软归属**：一篇文档可挂多个类目（带权重），避免硬分类漏检（吸取 H03 教训）。

## [S4] 语料树推理（查询期）——渐进披露导航

用**同一套推理挑选**逐层下钻，只展开 LLM 认为相关的分支（渐进披露）：

```
查询
 ├─ ① 领域层：LLM 看各领域摘要 → 挑相关领域（1-3 个）
 ├─ ② 类目层：在选中领域内，LLM 看类目摘要 → 挑相关类目
 ├─ ③ 文档层：在选中类目内，LLM 看文档标题/摘要 → 挑相关文档（map-reduce，复用 T9）
 └─ ④ 节点层：文档内树搜索（现有 L2/L3）→ 挑节点 → 取上下文
```

- 每层都是"**推理挑选，可变数量，宁缺毋滥**"（延续 T9 的 H02 修复）。
- 每层**只展开选中分支**，不遍历全树——海量下复杂度 = 相关分支大小，而非全库。
- L0 多通道召回作为**兜底/候选入口**：海量时先用 L0 粗筛出一个子集，再在该子集上建/走树。

## [S5] 对多跳连锁问答的支撑

语料树 + 逐层导航是**多跳的结构基础**：
- 跨文档：导航到不同分支取各自上下文，合并作答。
- 多跳连锁：导航到分支 A 抽取中间事实 → 用该事实作为下一轮查询导航到分支 B → 综合。

但**真正的多跳还需"推理-检索循环"**（见 [S6] P3）：树给了可导航的结构，迭代逻辑要在其上补。

**依赖**：P0 独立可先做；P1→P2 顺序；P3 依赖 P2 + pageindex-paper 多跳基准。

## [S7] 风险与开放问题

- **建树成本**：层级聚类 + LLM 定名是索引期一次性成本；增量更新策略需设计（否则每次加文档全量重建不可接受）。
- **聚类质量**：簇分得不好会导致领域层导航误判；软归属 + 向量+标签双信号缓解。需海量 benchmark 验证。
- **树导航 vs 扁平召回的取舍**：海量下纯树导航可能漏（树结构固化），L0 兜底必须保留。
- **多跳验证依赖基准**：P3 无法在 9 篇基准上验证，需 pageindex-paper 建多跳/跨文档基准（DuReader、中文 multi-hop 等，此前 hf-mirror 检索多数为空，需另寻数据源）。
- **与原文对齐**：本规划即原文 *PageIndex File System* 的自托管实现方向，可作为论文/专利的差异化点。
