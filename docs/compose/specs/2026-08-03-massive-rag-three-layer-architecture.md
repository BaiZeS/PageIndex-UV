# PageIndex-UV 面向海量多文档 RAG 的三层架构设计

> 日期：2026-08-03　状态：设计稿（未实施）
> 定位：选题面向**真实企业场景——在海量文档里做 RAG**。本文给出适配该目标的三层检索架构，
> 以及与现有代码的改造点和分阶段路线。

---

## [S1] 背景与定位

### [S1.1] 目标定位
PageIndex-UV 的目标任务是**海量多文档检索 + 问答**：给定数百至数千篇文档的语料库，
对每个查询先**不漏地**召回相关文档（召回@规模），再**精确地**定位并抽取答案（精确率）。
这不同于原文 PageIndex 的强项（**单文档内导航**，FinanceBench 98.7% 属此类）。

### [S1.2] 当前问题（根因已排查，见 investigation/regression/）
全套优化后 4 域 longdoc 平均 F1 从基线 0.853 降到 0.750。根因：
- **主因（H02）**：L1 选档从"整体挑选式"改成"独立逐篇打分"（`_score_candidates`），
  主题相近的硬负样本越过宽松阈值 `s_max×0.5`，导致"返回 5 篇只有 1 篇相关"（精确率稀释到 0.2）。
- **次因（H03）**：`_select_tag_sets` 作为**查询期硬过滤**，可能漏掉相关文档（4 条 recall=0）。

### [S1.3] 结构性盲区
当前 longdoc 基准是**每查询 9 篇**（1 正 + 8 负），只考"从 9 篇精排"，
**没有考海量场景的真正难点——"从千篇里不漏地召回"**。因此现有评测无法验证海量能力。

### [S1.4] 范式判断
原文 PageIndex 的成功来自 **agentic 推理式树搜索**（LLM 在树上推理导航、按需取数，"推理-导航"），
而非"打分-排序"。PageIndex-UV 的优化方向（打分式 L1）恰与之相反。**索引层保留，检索层需方向性回调。**

---

## [S2] 总体架构：三层 + 一条贯穿原则

**贯穿原则：便宜的在上层，昂贵的在下层。** 用便宜路由把千篇压到几十，昂贵的推理只花在这几十上。
如此延迟可控、精确率又高。

```
查询
  │
  ▼
[L0 语料路由层]  多通道并集召回（BM25+向量+实体+标签+元数据）
  │              目标：召回@规模，宁多勿漏；千篇 → 几十~上百候选
  ▼
[层级路由]       离线软聚类 hierarchy（域→类目→集合→文档）
  │              查询期只路由、不硬删；逐级缩小候选
  ▼
[推理选择层]     Map-Reduce 推理式选档（替代打分排序）
  │              目标：精确率；几十候选 → 3-5 篇
  ▼
[L2/L3 导航+上下文]  文档内树导航（保留现状）→ 答案抽取
```

## [S3] L0 语料路由层（召回@规模）

### [S3.1] 设计目标
海量候选里**不漏**相关文档。这是召回问题，over-retrieve，把精排留给下层。

### [S3.2] 通道选型
| 通道 | 实现 | 现状 | 角色 |
|:---|:---|:---|:---|
| BM25 倒排 | jieba `KeywordIndex`（已索引正文） | 现成 | 精确词匹配主力（产品名/案号/术语） |
| 向量稠密 | `bge-small-zh-v1.5`(512维) + ChromaDB | **实测离线可行** | 语义/改写召回，补 BM25 短板 |
| 实体图谱 | `entity_extractor` + `entity_relations` | 现成 | 实体中心查询路由（人/项目/组织） |
| 语义标签 | `closet_tags` | 现成 | 主题级召回 |
| 元数据过滤 | 部门/文类/时间 | **需新增** | 企业场景高效低成本 |

- **embedding 已定**：`bge-small-zh-v1.5`（ModelScope 拉取，96MB，离线加载实测通过，
  语义区分度正常：风控↔风控 0.806 / 风控↔肺炎 0.288）。`chroma_backend.py:91` 已支持
  `EMBEDDING_MODEL` 环境变量指向本地路径。
- 已知坑：hybrid+bge 在**短文本**曾返回空（解析器结构问题，已用 router 兜底修复）；结构化 longdoc 不受影响。

### [S3.3] 关键改动：从"加权截断"到"并集召回"
- **现状**（`super_tree.py` prefilter）：四通道加权求和 → `_truncate_candidates` 截断到 `_MAX_CANDIDATE_DOCS=50`。
- **改为**：各通道**分别召回 top-N → 取并集（union）→ 不提前截断**。保证召回多样性，避免过早丢弃。
- 新增元数据过滤通道（低成本高收益）。

## [S4] 层级路由（域→类目→集合→文档）

### [S4.1] 核心教训
之前"渐进披露形态1标签漏斗"是**查询期硬过滤**，会漏相关文档（根因 H03）。
海量下层级应**离线构建（索引期）**，查询期只路由、不硬删。

### [S4.2] 构建信号
- embedding 聚类（bge-small-zh 向量）+ 实体/标签 + LLM 辅助分类，**索引期一次性算好**。

### [S4.3] 软聚类而非硬归属
- 一篇文档可属于**多个"集合"并带权重**，避免"跨类目文档被硬路由漏检"（H03 翻版）。

### [S4.4] 层级作用
把"千篇里选"分解为"先选域/集合（便宜）→ 再集合内选文档（精确）"，逐级缩小候选规模。

---

## [S5] 推理选择层（修打分稀释 + 可扩展）

### [S5.1] 根因回顾
独立逐篇打分会让主题相近的硬负样本都越过阈值 → 精确率稀释。**"打分排序"天然不如"推理挑选"精确。**

### [S5.2] 方案对比
| 方案 | 可扩展性 | 精确率 | 适配海量 |
|:---|:---|:---|:---|
| 整体挑选（基线式） | 差（候选多超上下文） | 高 | 否 |
| 独立打分（当前 Q1） | 好 | **低（稀释）** | 否 |
| 锦标赛两两比较 | 调用多 | 高 | 一般 |
| **Map-Reduce 推理选择** | 好 | 高 | **推荐** |

### [S5.3] Map-Reduce 推理选择
- **Map**：把候选分组，每组让 LLM"推理挑出最相关的几篇"。
- **Reduce**：对各组胜出者再推理精选出最终 3-5 篇。
- 既扩展到海量候选，又保持"推理而非打分"，同时解决扩展性与精确率。
- **改造点**：替换 `super_tree.py` 的 `_score_candidates`；`select_documents` 改为调用 map-reduce。

## [S7] 分阶段实施路线

> **项目分工（D4）**：PageIndex-UV 聚焦自身代码/检索优化；数据集与实验评测由 pageindex-paper 负责。

1. **P0 建海量 benchmark**（每查询数百篇候选）：暴露"召回@规模"真实难点。【**pageindex-paper 负责**】
2. **P1 修 L1 精确率回归**：`_score_candidates` 打分 → 推理式选择（先整体挑选式止血）。【PageIndex-UV】
3. **P2 L0 并集召回 + 元数据通道 + 本地向量**：强化召回@规模。【PageIndex-UV】
4. **P3 离线软聚类层级路由**：建"域→类目→集合→文档"，查询期只路由。【PageIndex-UV】
5. **P4 Map-Reduce 推理选择**：海量候选下的精确选档。【PageIndex-UV】
> 每阶段用 P0 的海量 benchmark（pageindex-paper）+ 现有 9 篇基准双重验证。

## [S8] 风险与开放问题

- **延迟预算**：推理式选择比打分慢（更多 LLM 调用）。靠"便宜在上/昂贵在下"控制——推理只作用于 narrowed 候选。需给企业场景定延迟 SLA。
- **离线软聚类质量**：聚类错误会导致路由偏差。需软聚类+权重缓解，并在海量 benchmark 上验证。
- **向量通道规模**：ChromaDB 在千篇级的性能与增量更新需实测。
- **benchmark 真实性**：自生成海量语料能否代表真实企业文档分布，需后续用真实样本校准。
- **基线模型一致性**：基线(0801)与后续评测的 .env 配置历史未完全追溯（调查 H06 遗留）。
