## [S1] 设计命题

把 PageIndex"**单文档：先建树、再树上推理导航**"的范式推广到**海量多文档语料库**，并满足真实场景三大约束：
1. **语料库对用户是黑盒**，用户只给**笼统问题** → 检索必须完全由**语义理解**驱动。
2. **语料海量** → 纯树导航有扇出墙/成本/级联误判，需**按量级自适应** + 便宜的预筛。
3. **要多文档联合/连锁问答** → 需**图谱**补"跨分支实体关联 + 多跳"，需**循环推理**。

**核心判断（承接本轮讨论）**：
- 语义理解是**引擎**，语料树是**骨架**——树不替代语义理解，而是让语义理解在海量下能聚焦。
- 前置匹配**不取消**，而是**下沉为树导航每层的语义预筛**（skill/MCP 工具过滤范式）。
- 图谱**不是并列召回通道**，而是**织进树导航的加速器**（实体快捷跳转 / 预筛加权 / 多跳引导）。

## [S3] 语料统一结构树（骨架）——自动构建是核心能力

**前提（决定性）**：语料**无序进入，既无现成主题领域、也无业务维度**。因此"**自动按主题构建索引**"不是可选步骤，而是**系统地基**——与单文档 PageIndex 自动建章节树同一哲学，只是从文档内推广到文档间。

**层级结构**（整库一棵树）：

```
ROOT（知识库）
└── [主题聚类层 0..N]   ← 自动聚类生成；N 随语料量自适应（"领域/类目"是 N≥2 时的称呼）
    └── 文档 Document（真实、引用单元）
        ├─ 业务切面（可选元数据）：部门/项目/时间/客户…  ← 有才挂，没有就空
        └── 节点 Node（文档章节子树，真实）→ 子节点…
```

**层级本质（修正认知）**：
- **`文档→节点` 是真实稳定主干**（源文档固有）；其上的主题聚类层是**自动推断的脚手架**（可能错、可能不稳）。
- **"领域"与"类目"不是两种本质不同的层**——都是**主题聚类，只是粒度不同**。层数 N 由语料量自适应：小库 0 层、中库 1 层、海量 2 层，**不写死**。
- **软归属 ⇒ 技术上是 DAG**（一篇文档可挂多簇、带权重），导航体验上当树用；避免硬分类漏检（H03 教训）。

**业务维度 = 稀有切面，绝不做结构层**：业务维度（部门/项目/时间）常缺席，**不配当楼层**；作为文档上的**可选元数据切面**，仅在查询带业务上下文时用于过滤/加权，否则忽略（优雅降级）。

**自动构建管线（地基，完全无向量）**：

> 实证：PageIndex 单文档建树全程零向量（`page_index.py` 无任何 embedding 代码，纯 LLM）。语料树同理可完全无向量。

```
无序文档集
 ① 每篇索引时 LLM 抽取 closet_tags（3-5 个抽象语义标签，已有）
 ② 标签归一化：收集全库唯一标签 → LLM 合并同义词 → 规范标签集
     （对"标签集合"的有界一次性 LLM 操作；修复 风控/风险管理 不一致）
 ③ 用规范标签建 tag→docs 倒排表 → 确定性 group-by 分组
     （纯数据结构操作，不走 LLM、不占上下文）
 ④ LLM 递归生成上层结构（generate_toc_init/continue 模式）：
     对分组后的文档摘要分批 → 定名 + 生成摘要 + 组织上下级 + 裁定合并/拆分
 ⑤ 组装层级（粗簇→细簇→文档→章节树），软归属
 ⑥ 增量：新文档抽标签→归一→就近挂簇，挂不进则 LLM 判新开簇/并入
```

**增量两点细化（P1 必须实现）**：
- **标签归一（增量版）**：新文档标签先对**已有规范标签集**匹配（精确/同义映射表）；匹配不上再由 LLM 单点裁定"并入已有规范标签 or 新开"——单文档级有界调用，**不重跑全库归一**。
- **簇大小卡界的评估时机**：**每次插入时评估**——挂簇后簇规模超上限 → LLM 裁定拆分；低于下限 → 并入最近邻/上提父层（可延迟到下次结构调整）。不做周期性全量重建（[S12] 成本风险的对策）。

**分组不走 LLM、不阻塞上下文**：③是确定性倒排 group-by（O(n)）；LLM 只用于②标签归一（对标签集，有界）与④递归建树（分层分批、簇大小卡界），每次输入都有界。

**聚类粒度取向（用户决策）**：**偏细（多而细）**——更怕"主题太粗找不到"，胜过"层级太深绕晕"。之所以敢建细，是因为**语义预检索兜底扇出**：树细、每层兄弟多，但语义预筛先把候选压到 top-k，LLM 永不直面宽扇出。**细树负责"准"，预检索负责"不绕"。**

**细而不碎（平衡点）**：聚类越细越易"过碎"（把同主题文档切成太多小簇，反使相关内容分散）。需配**合并保护**：相似度过高的小簇自动合并，做到"细而不碎"（详见 [S3.1]）。

**命门**：②聚类 + ③LLM 定名摘要的质量——**自动造的树错了，比没有树更糟**（会隐蔽地误导导航）。

**保留**：单文档章节树原样作为树的最底层（PageIndex 核心不动）。

### [S3.1] 细而不碎：四机制 + 簇大小卡界

"碎"的害处 = 同主题内容被切成太多小簇、散落多处。防碎 = 要么别分开，要么分开了也能捞回。四机制分建树期/查询期两手：

**建树期（主动防碎）**：
1. **层次聚类天然多粒度**：相关内容在粗层共享祖先——细层分开了，粗层仍在一起；导航可在合适粒度工作。**树形本身就在防碎**。
2. **合并保护（主动闸门）**：过小的簇（< 阈值）并入最近邻/上提父层；过相似的兄弟簇合并。
3. **软归属**：跨主题文档挂多簇，不被硬切碎。

**查询期（碎而不漏）**：
4. **多簇选择 + 语义预筛**：导航不押注单一细簇（可变数量选多个相关细簇）；语义预筛把分散的相关内容捞回。

**簇大小双向卡界（同时防碎与防上下文爆）**：过小→合并（防碎）；过大→拆分（防单簇塞爆 LLM 上下文）。把簇卡在目标区间（如 10~50 篇/簇，需实测标定），保证每次 LLM 调用输入恒定可控。

**合并裁定方式**：向量为主已排除（无向量）→ **LLM 裁定**：在④递归生成时由 LLM 用语义判断哪些簇该合并/拆分（比阈值准），索引期一次性成本可接受。

## [S4] skill/MCP 加载范式的映射（核心借鉴）

海量 skill/MCP 的管理难题与海量文档**同构**——条目太多不能全进上下文。市场解法 = 渐进披露：

| skill/MCP 世界 | 语料树对应 |
|:---|:---|
| skill 描述（轻量元数据，热索引） | **树节点摘要** |
| skill 全文（命中才 lazy load） | **文档正文**（导航到才加载） |
| 技能按领域分类 + 导航 | **领域→类目层级** |
| **海量工具过滤**（语义预筛 top-k 再给模型） | **宽层语义预筛**（见下） |

**最关键的借鉴——宽层"工具过滤"**：MCP 管理海量工具不把全部工具给模型，而是**先语义预筛到 top-k 再让模型挑**。搬到树的宽层（无向量，用标签/关键词匹配）：

```
某层挂 1000 个兄弟节点（LLM 读不完）
  → 查询词/标签 匹配 1000 条节点摘要/标签（jieba + closet_tags 倒排，非向量）
  → 预筛 top-k 兄弟（毫秒级、便宜、保召回）
  → LLM 只在 top-k 里推理精挑（贵、保精确）
```

**深层意义**：前置匹配被**融进树导航每层**，不再是树外独立前置层 → 架构统一为"一套语义树导航"。这正是对"还要不要前置匹配"的最终回答：**匹配下沉为每层的语义预筛**。

## [S5] 量级自适应引擎

按语料规模自动选导航档位（类比 skill 按数量调加载策略）：

| 档位 | 触发 | 策略 |
|:---|:---|:---|
| **小**（几十篇） | 文档数 < 阈值 | 跳过层级，直接对全部文档摘要语义匹配 |
| **中**（几百篇） | 中等 | 单层领域路由 → 域内匹配 |
| **海量**（千篇+） | 大规模 | 完整层级树导航 + 宽层语义预筛 + 图谱加速 |

- 索引期/查询期**探测语料规模**（文档数、树宽）自动选档。
- 小语料不做无谓层级遍历；海量才上全套。**避免"小库也用重架构"的过度工程**（D2）。

## [S6] 语义树导航（检索核心）

每层统一执行"**预筛 → 加权 → 精挑**"（全程无向量）：
1. **语义预筛**（便宜、保召回）：用**查询词/标签 匹配 节点摘要/标签**（jieba 关键词 + closet_tags 倒排，非向量）把该层兄弟节点筛到 top-k（宽层才需要；窄层可跳过直接给 LLM）。closet_tags 是 LLM 抽取的语义标签，匹配它即"无向量的语义匹配"。
2. **图谱信号加权**：兄弟节点若含"查询链接到的实体"，加权提升（实体命中是比词面匹配更强的相关性证据）。
3. **LLM 推理精挑**（贵、保精确）：读 top-k 摘要，**可变数量挑选、宁缺毋滥**（延续 T9 的 H02 修复）。

- **渐进披露**：只展开选中分支，复杂度 = 相关分支大小，而非全库。
- **实体快捷跳转**：查询带实体时，图谱直接给出实体所在分支集合，**跳过自顶向下逐层导航**（直达电梯）。
- **兜底（点名现有实现）**：`_content_fallback`（`router.py:324`，jieba 分词 BM25 全文召回，已接线于 `router.py:410/436`）作安全网，补树导航漏掉的分支（防级联误判）。**不得新造向量兜底**——它已是无向量实现。
- **软归属去重**：同一文档可经多个簇分支命中（软归属 ⇒ DAG，见 [S3]）→ 选择结果与上下文组装均按 doc_id 去重，预算只计一次（现状 `_act_tree_search` 无去重，P2 改造时补上）。
- **延迟纪律**：每层 LLM 精挑是串行往返，延迟随深度线性增长；一层选中多个分支后，下一层导航**并行展开**（asyncio.gather）；精挑宁缺毋滥本身也在压缩展开量。

## [S7] 图谱辅助融合：构建 + 使用

**图谱与树正交互补**：树按**主题**组织（纵向层级，定位"内容在哪"）；图谱按**实体**连接（横向贯穿，连接"谁和谁相关"）。**两者都零向量、都在索引期构建**——索引期建两样东西：语料树 + 实体图谱。

### [S7.1] 图谱构建（索引期，LLM，零向量，与建树同期）

```
每篇文档索引时：
 ① 实体抽取（LLM）：从 标题+摘要+章节 抽实体（人物/项目/组织/概念）   [entity_extractor.extract_entities]
 ② 关系抽取（LLM）：抽实体间关系（works_on/authored/related_to…）     [extract_relations]
 ③ 存储：entities(按 name+type 去重) / entity_mentions(实体→文档/节点) / entity_relations(三元组)
 ④ 跨文档链接：同名实体自动合并成一个节点（insert_entity ON CONFLICT）→ 把不同文档串起来
```

**实体消歧（一致性缺口，需补）**：`insert_entity` 按**精确名字**去重，`"张三"/"小张"` 同一人会被当成两个实体、连不起来——与标签"风控/风险管理"同类问题。需补**实体消歧步**：抽取后对全库实体归一（合并别名/同义实体），让同一实体唯一化。**与标签归一化同构——对"实体集合"的有界 LLM 操作**（`aliases`+`_fuzzy_match` 已部分具备，但现有 `_fuzzy_match`（`entity_extractor.py:221`）**只做单文档内**关系提及→实体的匹配，跨文档归一需新建；增量场景对齐标签归一的增量版：新实体先查已有规范集，不中再 LLM 单点裁定）。

### [S7.2] 图谱使用（查询期，三件套）

图谱**不是并列召回通道**，而是织进树导航的三个加速器，补树"按主题切、切散了实体"的盲区：

| 件 | 作用 | 用在哪 | 对应现有函数 |
|:---|:---|:---|:---|
| **① 实体快捷跳转** | 查询带实体 → 图谱直达实体所在分支，省逐层导航 | S6 导航入口 | `search_entities`→`get_entity_documents` |
| **② 预筛信号增强** | 含查询链接实体的节点加权，助预筛顶上来 | S6 每层预筛 | 实体命中加权 |
| **③ 多跳导航** | 抽出中间实体后，图谱查其关系/共现文档，引导下一跳 | S8 循环推理 | `get_entity_relations` |

- **前置改造（P3 必做，不可直接复用）**：现有 `search_entities`（`db.py:566-578`）是**整条查询串的 LIKE 匹配**（`name LIKE '%query%'`），多词查询几乎永不命中（现状两个调用点 `super_tree.py:264`、`router.py:287` 都传整串）。三件套依赖它之前，必须先改为**分词匹配**（jieba 查询词 vs 实体 name/aliases，去停用词），否则①②形同虚设。
- **价值边界**：图谱增益取决于**实体型/多跳查询占比**；纯笼统无实体查询，图谱退到仅多跳场景。

## [S8] 循环推理（多跳支撑）

当前管线是**单轮**召回+作答，答不了"先查 A 才知道去 B 查什么"的连锁问答。补**推理-检索循环**：

```
查询 → 判断可否分解
  ├─ 不可分解 → 单次树导航作答
  └─ 可分解 → 循环：
       树导航到分支A → 抽取中间实体/事实
       → 图谱③ 查关系/共现 → 引导下一跳到分支B
       → … → 综合各跳上下文作答
```

- 树给了**可导航的结构**，循环逻辑在其上补**迭代**。
- 图谱③让"下一跳去哪"由实体关系精准引导，而非拿中间词重新全库匹配。

## [S12] 风险与开放问题

- **建树/增量成本**：聚类+LLM 定名是索引期成本；增量策略不设计好会每次全量重建。
- **摘要质量**：节点摘要是导航元数据命门，质量差则导航崩。
- **级联误判**：笼统查询顶层选错分支会向下放大；靠多分支探索+语义兜底缓解。
- **查询延迟**：逐层 LLM 精挑 + 多跳循环是串行往返，延迟随深度/跳数线性增长；缓解 = 分支并行展开（[S6] 延迟纪律）+ 宁缺毋滥压缩展开量；延迟目标需实测标定。
- **图谱增益依赖查询构成**：实体/多跳占比低则图谱价值有限。
- **多跳验证卡基准**：P4 无法在 9 篇基准验证；需 pageindex-paper 建多跳基准（DuReader/中文 multi-hop，数据源待找）。
- **量级阈值标定**：小/中/海量分档阈值需实测标定。

## [S13] 决策记录（本轮收口）

- **树为主**：语料统一结构树是主干，单文档树推理推广到全库（用户确认）。
- **skill/MCP 范式**：元数据热索引 + 按需加载 + 宽层工具过滤（语义预筛）；前置匹配下沉为每层预筛。
- **量级自适应**：小直连 / 中单层 / 海量层级树（用户提出）。
- **图谱辅助**：三件套（实体快捷跳转 / 预筛加权 / 多跳引导），非并列通道（用户确认"树为主、图为辅"）。
- **语义理解为引擎**：笼统查询驱动，树是骨架；相似度≠相关性，不做扁平向量检索。
- **自动构建是核心**（2026-08-04 补充）：语料无序进入、无现成主题/业务维度 → 自动主题建树是地基，非可选步骤。
- **层级本质修正**：领域/类目 = 主题聚类的自适应粒度档位（非两种固定层）；深度 N 随语料量自适应；`文档→节点`是真实主干，其上是自动脚手架；软归属⇒DAG。
- **业务维度 = 稀有切面**：常缺席 → 绝不做结构层，仅可选元数据切面，查询带业务上下文时过滤/加权。
- **聚类粒度 = 偏细（多而细）**：更怕"主题太粗找不到"胜过"层级太深绕晕"；敢建细是因语义预检索兜底扇出（细树负责准、预检索负责不绕）。需"细而不碎"合并保护（见 [S3.1]）。
- **完全无向量建树（用户定稿）**：实证 PageIndex 单文档建树零向量（page_index.py 无 embedding 代码）→ 语料树也完全无向量。管线 = 每篇抽 closet_tags → 标签归一化（LLM 合并同义，修复不一致）→ 确定性倒排 group-by 分组（不走 LLM、不占上下文）→ LLM 递归生成上层结构（init/continue）。分组不阻塞上下文（确定性操作）；LLM 只对标签集/分层分批建树，输入有界。
- **细而不碎四机制**：层次聚类多粒度 + 合并保护 + 软归属（建树期）+ 多簇选择/预筛（查询期）；簇大小双向卡界（过小合并防碎、过大拆分防上下文爆）；合并由 LLM 语义裁定。
- **图谱构建+使用定稿**：索引期与树同期建图谱（实体/关系抽取→实体消歧→三元组存储→同名实体跨文档链接）；实体消歧对齐标签归一化思路（修复 张三/小张 不链接）。使用 = 三件套（快捷跳转/预筛加权/多跳引导）。树按主题纵向、图谱按实体横向，正交互补，均零向量。
